# فاز صفر خریدینو — ممیزی اولیه و خط مبنا

**وضعیت:** پیش‌نویس اولیه فاز صفر  
**بازار شروع:** ایران  
**شاخه مبنا:** `feature/kharidino-gaming-premium-integrated-2026-10-05`  
**شاخه توسعه:** `feature/kharidino-explore`

## ۱. هدف محصول

خریدینو به‌عنوان یک ابرپلتفرم چندبخشی طراحی می‌شود؛ هسته اصلی آن بازار چندفروشندگی و مقایسه قیمت است و در کنار آن تجربه‌های رسانه‌ای و خدماتی قرار می‌گیرند:

- بازار کالا و خدمات با فروشندگان متعدد، پیشنهادهای قابل مقایسه و مسیر خرید قابل رهگیری.
- سینما در دو مسیر مستقل اما مرتبط: تماشای آنلاین فیلم/سریال و جست‌وجو/رزرو بلیت سینما.
- Explore برای کشف محتوای تصویری و ویدئویی، با امکان اتصال محتوا به محصول یا فروشگاه.
- اپلیکیشن اندروید در دو شکل: تجربه Native و تجربه WebView، بر پایه API مشترک.
- توسعه تدریجی امکانات متناسب با گروه‌های مختلف کاربران؛ نه عرضه همه قابلیت‌ها در نسخه اول.

## ۲. شواهد ممیزی از مخزن فعلی

این ممیزی بر فایل‌های قابل مشاهده در شاخه مبنا انجام شده است؛ هنوز جایگزین اجرای تست و بررسی کامل نسخه محلی نیست.

### موارد موجود طبق README و کد راه‌انداز

- هسته Flask و جریان کاتالوگ، محصول، فروشگاه، دسته‌بندی، سبد و سفارش.
- Marketplace چندفروشندگی، پیشنهادهای فروشگاه و قابلیت مقایسه پیشنهادها.
- چرخه پرداخت با وضعیت‌های تراکنش، idempotency و Gateway abstraction.
- Test Gateway و مسیر اتصال NextPay در کد؛ README تصریح می‌کند درگاه واقعی باید با API رسمی و تنظیمات Production تکمیل شود.
- حسابداری و تسویه فروشندگان، گردش وضعیت سفارش و کنترل‌های امنیتی.
- API موبایل در مسیر `/api/mobile` برای سلامت، دسته‌بندی، فهرست/جزئیات محصول و جست‌وجو؛ API فعلی در کد بررسی‌شده عمدتاً فقط‌خواندنی است.
- راه‌انداز `run_kharidino.py` که ماژول‌های مختلف را روی Flask app ثبت می‌کند.

### مواردی که در ممیزی اولیه، پیاده‌سازی‌شده محسوب نمی‌شوند

- ماژول کامل Explore و فید ویدئو/تصویر.
- سامانه مدیریت دارایی رسانه‌ای، پردازش ویدئو، پخش تطبیقی و CDN.
- کاتالوگ دارای مجوز پخش فیلم/سریال و سرویس پخش آنلاین.
- یکپارچه‌سازی رزرو صندلی و بلیت سینما با سالن‌ها/سینماها.
- اپلیکیشن Native اندروید مستقل و پوسته WebView محصولی.
- اتصال عملیاتی درگاه بانکی Production؛ وجود adapter به‌تنهایی به معنی فعال بودن درگاه واقعی نیست.

## ۳. تصمیم‌های معماری اولیه

### ۳.۱ سبک معماری

در فاز اول، **Modular Monolith** بر پایه Flask حفظ می‌شود؛ هر دامنه مرز، مدل، سرویس، API و تست مستقل خواهد داشت. فعلاً مهاجرت به microservices توصیه نمی‌شود؛ استخراج سرویس مستقل فقط وقتی انجام شود که بار عملیاتی، تیم یا نیاز مقیاس‌پذیری آن را توجیه کند.

دامنه‌های پیشنهادی:

1. Identity & Access — حساب، نقش، احراز هویت و رضایت‌ها.
2. Marketplace — محصول، دسته، فروشگاه، پیشنهاد، مقایسه قیمت، سبد، سفارش و مرجوعی.
3. Payments & Ledger — پرداخت، بازپرداخت، دفتر مالی و تسویه.
4. Media & Explore — بارگذاری، پردازش، انتشار، فید، تعامل و پیوند محتوا به محصول/فروشگاه.
5. Cinema — کاتالوگ محتوا، حقوق نمایش، اشتراک/دسترسی، پخش و رزرو بلیت سینما.
6. Mobile API — قراردادهای نسخه‌بندی‌شده و مشترک برای Native و WebView.
7. Notifications & Support — اعلان، پشتیبانی، گزارش تخلف و رسیدگی.

### ۳.۲ بازار ایران، پول و قیمت

- بازار عملیاتی نسخه اول: ایران.
- واحد ذخیره‌سازی پول باید در کل سامانه یکپارچه و صریح باشد؛ قبل از هر مهاجرت داده، واحد فعلی ستون‌های قیمت و مبلغ سفارش بررسی شود. از روی عدد صحیح موجود نمی‌توان نتیجه گرفت که داده‌ها ریال‌اند یا تومان.
- تصمیم پیشنهادی: مبلغ‌ها به‌صورت عدد صحیح در کوچک‌ترین واحد داخلی مصوب ذخیره شوند؛ تبدیل ریال/تومان فقط در مرز ورودی/نمایش و با نام‌گذاری صریح انجام شود. تصمیم نهایی و migration پس از ممیزی داده موجود ثبت شود.
- قیمت، تخفیف، کارمزد، مالیات، بازپرداخت و تسویه باید از هم تفکیک شوند؛ محاسبات مالی با float انجام نشود.
- درگاه‌ها از طریق adapter مستقل ارائه شوند. انتخاب PSP، قرارداد callback، کلیدها و سناریوهای بازپرداخت باید با مستندات رسمی ارائه‌دهنده و الزامات ایران تأیید شود.
- پشتیبانی از ارزهای خارجی و بازار بین‌المللی در مدل توسعه آینده دیده می‌شود، اما فعال‌سازی آن به فاز بعد، نرخ تبدیل معتبر، قواعد حسابداری و بررسی حقوقی/عملیاتی موکول است.

### ۳.۳ سینما: دو محصول مجزا

**الف) پخش آنلاین:** کاتالوگ فیلم/سریال، فصل و قسمت، جست‌وجو، رده‌بندی سنی، حق پخش، پنجره و قلمرو مجاز، سطح دسترسی/اشتراک، سابقه تماشا و پخش امن. هیچ محتوایی بدون اثبات مجوز و قلمرو نمایش منتشر نمی‌شود.

**ب) رزرو بلیت:** شهر، سینما، سالن، سانس، نقشه صندلی، نگه‌داشت موقت صندلی با انقضا، پرداخت، صدور بلیت دارای شناسه یکتا، کنترل ورود، لغو و استرداد. اتصال به سامانه هر سینما/تأمین‌کننده باید adapter جداگانه داشته باشد. موجودی صندلی باید اتمیک باشد تا فروش تکراری رخ ندهد.

این دو مسیر از نظر تجربه کاربر زیر برند «سینما» قرار می‌گیرند، اما مدل داده، جریان درآمد، مجوز و عملیاتشان یکی نیست.

### ۳.۴ Explore و رسانه

- فید ترکیبی تصویر، ویدئوی کوتاه و ویدئوی بلند.
- نمایش کارت/شبکه‌ای برای کشف و ورود به پخش‌کننده تمام‌صفحه.
- هر محتوا مالک، وضعیت انتشار، سطح نمایش، توضیح، برچسب، فایل اصلی، تصویر بندانگشتی و آمار پایه دارد.
- محتوا می‌تواند به محصول، پیشنهاد فروشنده یا صفحه فروشگاه لینک شود؛ خرید در MVP از مسیر امن فروشگاه/محصول انجام می‌شود و checkout درون فید تعریف نمی‌شود.
- فایل رسانه‌ای در object storage نگهداری شود؛ پردازش پس‌زمینه برای اعتبارسنجی، تولید thumbnail، transcode و renditionهای HLS/DASH؛ تحویل از CDN. نگهداری فایل حجیم در دیتابیس یا دیسک محلی وب‌سرور راهبرد Production نیست.
- کنترل نوع واقعی فایل، اندازه، مدت، سهمیه، اسکن بدافزار، گزارش محتوا، moderation، محدودیت نرخ و حذف/تعلیق حساب لازم است.
- نسخه اول با فید ساده و مرتب‌سازی قابل توضیح آغاز می‌شود؛ الگوریتم توصیه‌گر پیچیده پس از جمع‌آوری داده رضایت‌مندانه و تعریف سیاست حریم خصوصی.

### ۳.۵ اندروید: Native و WebView

- یک API نسخه‌بندی‌شده مشترک، منبع حقیقت داده و منطق کسب‌وکار است.
- اپ Native مستقل برای تجربه‌های اصلی موبایل، اعلان Push، deep link، مجوزهای دستگاه و تعامل روان.
- WebView برای نمایش کنترل‌شده صفحات وب/جریان‌هایی که باید سریع با سایت همگام شوند؛ پل JavaScript محدود و allowlist شده، مدیریت امن نشست و لینک‌های خارجی.
- پرداخت در WebView یا Native باید فقط از جریان تأییدشده سرور عبور کند؛ اطلاعات حساس کارت هرگز در اپ ذخیره نشود.
- Native و WebView دو پوسته برای یک backend هستند، نه دو سامانه سفارش/پرداخت جداگانه.

## ۴. الزامات غیرعملکردی و امنیت

- Production روی پایگاه‌داده تراکنشی مناسب مانند PostgreSQL؛ SQLite برای توسعه/تست یا استقرار کوچک کنترل‌شده باقی بماند، پس از بررسی migration و سازگاری.
- صف و worker برای transcode رسانه، اعلان، گزارش‌گیری و کارهای زمان‌بر.
- ذخیره‌سازی رسانه جدا از دیتابیس؛ backup، retention و disaster recovery.
- RBAC برای خریدار، فروشنده، تولیدکننده محتوا، اپراتور سینما، پشتیبانی و مدیر.
- audit log برای تغییرات مالی، دسترسی ادمین، انتشار محتوا و عملیات رزرو.
- حریم خصوصی: حداقل‌سازی داده، رضایت برای اعلان/شخصی‌سازی، سیاست نگهداری و حذف، و محدودیت دسترسی کارکنان.
- observability: log ساختاریافته، metrics، tracing در مسیرهای حساس، health checks و هشدار.
- دسترس‌پذیری و پشتیبانی RTL/فارسی، اعداد/تاریخ محلی و طراحی مناسب اینترنت کم‌سرعت.

## ۷. الحاقیه ممیزی فنی تکمیلی — بررسی مدل داده و Android

این الحاقیه پس از بررسی مستقیم مدل‌های `app.py`، فایل‌های Android و API موبایل اضافه شده است.

### ۷.۱ مدل پول و پایگاه داده

در مدل‌های بررسی‌شده، مقادیر پولی به‌صورت `Integer` تعریف شده‌اند؛ از جمله:

- `Product.price`
- `Offer.price`
- `Order.total`
- `OrderItem.price`
- `Invoice.subtotal`, `discount`, `tax`, `total`
- `PriceAlert.target_price`
- `PriceHistory.price`

در این فیلدها، currency code یا نام واحد پول ذخیره نمی‌شود. بنابراین **واحد واقعی رکوردهای موجود از تعریف مدل قابل اثبات نیست**. اپ Android در صفحه فعلی قیمت را با پسوند «تومان» نشان می‌دهد، اما این برچسب برای اثبات واحد تمام رکوردهای قدیمی کافی نیست.

**تصمیم اجرایی:** تا زمان ممیزی نمونه‌های واقعی دیتابیس و مسیرهای ورود قیمت، هیچ تبدیل ریال/تومان و هیچ migration روی مقادیر مالی انجام نشود. ابتدا منبع داده، فرم‌های ورود، seedها، فاکتور، گزارش حسابداری، درگاه و تست‌ها تطبیق داده شوند. سپس قرارداد واحد پول و migration قابل rollback تصویب شود.

تنظیم فعلی `SQLALCHEMY_DATABASE_URI` در `app.py` به فایل SQLite محلی `kharidino.db` اشاره می‌کند. مهاجرت به PostgreSQL می‌تواند برای استقرار مقیاس‌پذیر در نقشه راه بماند، اما باید جداگانه طراحی و آزمایش شود؛ این ممیزی هنوز مهاجرت یا سازگاری کامل را اثبات نمی‌کند.

### ۷.۲ وضعیت واقعی Android

در مخزن، پایه Native اندروید واقعاً وجود دارد:

- پروژه Gradle با Kotlin.
- رابط Jetpack Compose در `MainActivity.kt`.
- API client مبتنی بر Retrofit.
- مدل و endpointهای ابتدایی برای فهرست محصولات از API موبایل.
- workflow انتشار Android در GitHub Actions.

اما نمونه فعلی `MainActivity.kt` یک صفحه آغازین ساده است: فهرست محصولات را می‌خواند و نوار ناوبری نمایشی دارد؛ در این فایل، جریان کامل ورود، سبد، پرداخت، سفارش، اعلان، Explore و سینما پیاده‌سازی نشده است. بنابراین وضعیت صحیح «Native starter موجود، اپ کامل و آماده انتشار نیست» است.

در فایل‌ها و مسیرهای بررسی‌شده، پیاده‌سازی WebView محصولی شناسایی نشد. مسیر WebView باید به‌عنوان بخش جداگانه طراحی و با allowlist، محدودیت پل JavaScript، مدیریت امن نشست و تست امنیتی ساخته شود.

### ۷.۳ وضعیت واقعی رسانه

در `app.py` پسوندهای مجاز تصویر و ویدئو تعریف شده‌اند و مسیر آپلود پس‌زمینه می‌تواند ویدئو بپذیرد؛ همچنین محدودیت کلی درخواست ۱۰۰ مگابایت تعریف شده است. این قابلیت با سامانه رسانه‌ای کامل تفاوت دارد.

در بررسی ساختار شاخه مبنا، ماژول کامل انتشار محتوا، پردازش پس‌زمینه ویدئو، transcode، HLS/DASH، moderation و CDN به‌عنوان یک زیرسامانه Explore شناسایی نشد. این موارد همچنان توسعه جدید محسوب می‌شوند.

### ۷.۴ نتیجه اصلاح‌شده

- Android Native: پایه اولیه موجود است و باید تکمیل شود؛ شروع از صفر لازم نیست.
- Android WebView: در ساختار بررسی‌شده پیاده‌سازی محصولی آن شناسایی نشد.
- واحد پول: هنوز نامشخص؛ برچسب تومان در UI قرینه است، نه مدرک قطعی داده.
- SQLite: پایگاه‌داده فعلی کد؛ PostgreSQL گزینه معماری استقرار آینده، نه وضعیت فعلی.
- ویدئو: پشتیبانی محدود پسوند/آپلود وجود دارد؛ پلتفرم رسانه و پخش هنوز باید ساخته شود.

این الحاقیه صرفاً مستندات را دقیق‌تر می‌کند و هیچ تغییری در مدل داده، پایگاه‌داده یا کد اجرایی ایجاد نمی‌کند.
