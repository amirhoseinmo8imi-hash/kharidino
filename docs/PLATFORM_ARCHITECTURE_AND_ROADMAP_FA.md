# معماری و نقشه راه ابرپلتفرم خریدینو

> سند پایه توسعه وب، اپ اندروید و API مشترک. تصمیم محصول: بازار، سینما و اپلیکیشن همگی در وب و اپ تجربه کامل داشته باشند و اکسپلور یکی از هسته‌های اصلی تجربه باشد.

## 1. چشم‌انداز محصول

خریدینو یک ابرپلتفرم برای خرید، سرگرمی، یادگیری و خدمات است. کاربر با یک حساب واحد به این بخش‌ها دسترسی دارد:

- **بازار:** چندفروشندگی، کاتالوگ کالا، مقایسه قیمت، سبد، سفارش، مرجوعی و پنل فروشنده.
- **اکسپلور:** فید شخصی‌سازی‌شده عکس و ویدئو، پست و کلیپ، دنبال‌کردن سازنده‌ها و فروشگاه‌ها، پسندیدن، نظر، ذخیره و اشتراک‌گذاری؛ اتصال محتوا به محصول، فروشگاه و فیلم.
- **سینما:** فیلم و سریال، صفحه جزئیات، پخش ویدئو، ادامه تماشا و علاقه‌مندی؛ همچنین سینمای حضوری، سانس، انتخاب صندلی، رزرو و بلیت QR.
- **نقشه:** کشف فروشگاه‌ها، سینماها و مراکز خدماتی و نمایش موقعیت و مسیر.
- **آموزش و خدمات:** دوره‌ها، محتوای آموزشی، ارائه‌دهندگان خدمات و درخواست یا رزرو.
- **اپ اندروید:** یک اپ واحد برای همه بخش‌ها، متصل به API مشترک.
- **زیرساخت مشترک:** حساب و نقش‌ها، اعلان‌ها، پرداخت، کیف پول، پشتیبانی، گزارش‌گیری، امنیت و مدیریت.

## 2. اصول معماری

1. **API-first:** منطق کسب‌وکار از رابط وب جدا و از API نسخه‌بندی‌شده با پایه /api/v1 ارائه شود.
2. **Modular Monolith در شروع:** با توجه به هسته فعلی Flask، ابتدا برنامه ماژولار با مرزهای دامنه روشن؛ نه microservice زودهنگام.
3. **یک هویت، چند تجربه:** حساب، نشست یا توکن، نقش‌ها، تنظیمات و اعلان‌ها مشترک باشند؛ مجوزها در سرور کنترل شوند.
4. **مالکیت داده:** بازار، اکسپلور، سینما، نقشه، آموزش و پرداخت مرز داده و سرویس مستقل داشته باشند.
5. **وب و اندروید هم‌ارز:** قابلیت‌های اصلی بازار، اکسپلور و سینما در هر دو بستر قابل استفاده باشند.
6. **رسانه به‌عنوان زیرساخت:** آپلود امن، پردازش تصویر و ویدئو، thumbnail، streaming تطبیقی، کنترل دسترسی و گزارش سوءاستفاده مشترک باشد.
7. **امنیت و حریم خصوصی از ابتدا:** حداقل‌سازی داده، کنترل دسترسی، ثبت رویدادهای حساس و حفاظت از فایل‌ها.
8. **سازگاری با کد موجود:** تغییرات additive، migration کنترل‌شده و تست رگرسیون؛ حفظ قابلیت‌های فعلی تا جایگزینی امن.

## 3. نمای لایه‌ای هدف

~~~text
وب واکنش‌گرا (Flask/Jinja فعلی)       اپ اندروید (Kotlin)
                 \                    /
                  API Gateway / BFF
                          |
             احراز هویت، مجوز و نسخه API
                          |
  -------------------------------------------------------
  | بازار | اکسپلور | سینما | نقشه | آموزش و خدمات |
  -------------------------------------------------------
  | کاربران و پروفایل | اعلان | جستجو | پرداخت و کیف پول |
  -------------------------------------------------------
                          |
     PostgreSQL (تراکنشی) + Redis (cache/queue)
                          |
   Object Storage + CDN + پردازش رسانه + Video Streaming
                          |
        درگاه پرداخت، پیامک/ایمیل، نقشه و سرویس بیرونی
~~~

این نمای هدف است، نه ادعای وجود همه اجزا در نسخه فعلی. در فاز اول Flask و SQLAlchemy حفظ می‌شوند؛ دامنه‌ها به Blueprint، service و repository مستقل تفکیک می‌شوند. Redis، صف پردازش و ذخیره‌سازی ابری بر اساس نیاز واقعی اضافه خواهند شد.

## 4. مرزبندی ماژول‌ها

| ماژول | مسئولیت و داده‌های اصلی |
|---|---|
| Identity | User، Profile، Role، Session/Token، Consent |
| Marketplace | Store، Product، Variant، Offer، Inventory، Cart، Order، Return |
| Explore | Post، Media reference، Feed، Follow، Like، Comment، Bookmark، Report |
| Cinema | Title، Season/Episode، VideoAsset، PlaybackProgress، Theater، Showtime، Seat، Booking، Ticket |
| Media | Upload، Asset، Rendition، Thumbnail، TranscodeJob، AccessPolicy |
| Discovery/Map | GeoLocation، Place، Category و جستجوی جغرافیایی |
| Learning/Services | Course، Lesson، Provider، Service، Appointment/Request |
| Payments | PaymentIntent، Transaction، Refund، Wallet، Ledger، Settlement |
| Notifications | اعلان درون‌برنامه‌ای، Push، پیامک/ایمیل و ترجیحات |
| Admin/Support | Moderation، AuditLog، Reports، SupportTicket، FeatureFlags |

قانون مالکیت: اکسپلور مالک پست و تعامل اجتماعی است؛ محصول و فیلم فقط با شناسه مرجع به پست متصل می‌شوند. فایل رسانه‌ای در ماژول Media مدیریت می‌شود.

## 5. قرارداد API پیشنهادی

- پایه: /api/v1
- هویت: /auth/register، /auth/login، /auth/refresh، /auth/logout، /auth/me
- بازار: /market/products، /market/offers، /market/stores، /market/cart، /market/orders
- اکسپلور: /explore/feed، /explore/posts، /explore/posts/{id}/likes، /explore/posts/{id}/comments، /explore/follows
- سینما: /cinema/titles، /cinema/titles/{id}، /cinema/playback-sessions، /cinema/progress، /cinema/theaters، /cinema/showtimes، /cinema/bookings
- نقشه: /map/places و /map/stores
- آموزش و خدمات: /learning/courses، /services/providers، /services/requests
- رسانه: /media/uploads، /media/assets/{id}
- پرداخت: /payments/intents، /payments/{id}/status، /wallet

همه endpointهای نوشتنی باید احراز هویت، مجوز، CSRF در وب یا اعتبارسنجی توکن در موبایل، rate limit و اعتبارسنجی ورودی داشته باشند. عملیات مالی باید idempotency key داشته باشند.

## 6. ناوبری یکپارچه

ناوبری اصلی وب و اپ: **خانه | بازار | اکسپلور | سینما | نقشه | حساب**

اکسپلور باید هم‌سطح بازار و سینما در ناوبری سطح اول باشد، نه زیرمنوی بازار. آموزش و خدمات از خانه و بخش بیشتر قابل دسترسی‌اند.

## 7. نقشه راه اجرایی

### فاز 0 — ممیزی و تثبیت پایه
- فهرست‌برداری routeها، مدل‌ها، قالب‌ها و قابلیت‌های موجود.
- ترسیم وابستگی‌ها و شناسایی بخش‌های تکراری یا ناقص.
- تعریف قرارداد API، استاندارد خطا، pagination و مجوزها.
- تثبیت CI، تست‌ها، migration و محیط توسعه.
- خروجی: سند وضعیت موجود و backlog اولویت‌بندی‌شده.

### فاز 1 — هویت بصری و پوسته ابرپلتفرم
- طراحی صفحه اصلی و navigation یکپارچه RTL.
- ورودی‌های روشن بازار، اکسپلور، سینما، نقشه و خدمات.
- سیستم مؤلفه‌ها، رنگ، تایپوگرافی، حالت موبایل و دسترس‌پذیری.
- خروجی: پوسته مشترک وب و راهنمای طراحی.

### فاز 2 — بازار و مقایسه قیمت
- تکمیل چندفروشندگی، کاتالوگ، پیشنهاد قیمت و موجودی.
- مقایسه فروشندگان برای یک محصول، فیلتر و مرتب‌سازی.
- سبد، checkout، سفارش و وضعیت قابل رهگیری.
- پنل فروشنده و API آماده اپ.
- خروجی: مسیر خرید end-to-end.

### فاز 3 — اکسپلور (هسته مستقل و حیاتی)
- مدل پست و رسانه، آپلود امن و پردازش تصویر/ویدئو.
- فید اولیه با pagination و رتبه‌بندی ساده و قابل توضیح.
- پروفایل سازنده و فروشگاه، follow، like، comment، bookmark و report.
- اتصال پست به محصول، فروشگاه و عنوان سینمایی.
- moderation، گزارش محتوا و کنترل حریم خصوصی.
- خروجی: اکسپلور واقعی و قابل استفاده، نه صفحه نمایشی.

### فاز 4 — خریدینو سینما و ویدئو
- کاتالوگ و صفحه جزئیات فیلم و سریال.
- ذخیره پیشرفت تماشا، فهرست و ادامه تماشا.
- خط لوله رسانه: آپلود، transcode، چند کیفیت، HLS/DASH، CDN و مجوز پخش.
- مدیریت حقوق محتوا و گزارش پخش.
- سینمای حضوری: سالن، سانس، نقشه صندلی، رزرو اتمیک، پرداخت و بلیت QR.
- خروجی: پخش کنترل‌شده و جریان رزرو قابل تست. محتوای دارای حق نشر فقط با مجوز عرضه شود.

### فاز 5 — آموزش، خدمات و امکانات اجتماعی
- دوره، درس، مدرس و پیشرفت آموزشی.
- فهرست ارائه‌دهندگان خدمات، درخواست و رزرو.
- توسعه پروفایل، دنبال‌کردن موضوعات و اعلان اجتماعی.

### فاز 6 — اپلیکیشن اندروید
- اپ native با Kotlin و Jetpack Compose و معماری UI/domain/data.
- اتصال به API نسخه‌بندی‌شده و مدیریت امن نشست و refresh token.
- deep link برای محصول، پست، فیلم، فروشگاه و بلیت.
- push notification، آپلود رسانه، پخش ویدئو و مدیریت شبکه ضعیف.
- خروجی: اپ واحد خریدینو برای بازار، اکسپلور، سینما و سایر ماژول‌ها.

### فاز 7 — کیف پول، پرداخت، امنیت و مدیریت
- اتصال درگاه واقعی با callback verification و idempotency.
- کیف پول و دفترکل دوبل، refund، تسویه فروشنده و تطبیق مالی.
- پنل مدیریت کاربران، محتوا، فروشندگان، فیلم‌ها، سفارش‌ها و گزارش‌ها.
- ممیزی دسترسی، امنیت API، تست نفوذ و حفاظت داده.

### فاز 8 — آزمون، انتشار و رشد
- تست واحد، integration، end-to-end، بار و امنیت.
- پایش خطا، لاگ ساختاریافته، metrics، backup و disaster recovery.
- انتشار مرحله‌ای، feature flag، بازخورد کاربران و بهبود مستمر.

## 8. ترتیب اولویت

1. ممیزی کد و تثبیت معماری.
2. پوسته یکپارچه و ناوبری؛ اکسپلور هم‌سطح بازار و سینما.
3. تکمیل بازار موجود و API آن.
4. اکسپلور end-to-end.
5. سینما و زیرساخت پخش ویدئو.
6. آموزش و خدمات.
7. اپ اندروید بر پایه APIهای پایدار.
8. تکمیل کیف پول و پرداخت، سخت‌سازی و انتشار؛ امنیت پایه از روز اول ادامه دارد.

## 9. معیار پذیرش هر فاز

- قابلیت از رابط تا API و پایگاه داده کار کند؛ منو یا صفحه استاتیک کافی نیست.
- مجوزها در سرور کنترل شوند و داده خصوصی افشا نشود.
- تست مسیر موفق، خطا، ورودی نامعتبر و دسترسی غیرمجاز وجود داشته باشد.
- migration و برنامه بازیابی مستند باشد.
- موبایل، دسکتاپ، RTL و دسترس‌پذیری بررسی شوند.
- قابلیت نیمه‌تمام به‌عنوان کامل معرفی نشود.

## 10. محدوده شروع در مخزن فعلی

مخزن فعلی بر پایه Flask، Jinja و SQLAlchemy است. شروع امن:
- حفظ برنامه فعلی و استخراج تدریجی ماژول‌های دامنه؛
- افزودن APIهای /api/v1 بدون شکستن routeهای وب؛
- ممیزی وضعیت واقعی اکسپلور و سینما پیش از توسعه مجدد؛
- نگه‌داشتن نقشه به‌عنوان ماژول مستقل Discovery؛
- ساخت اپ اندروید پس از تثبیت قرارداد APIهای هسته.

این سند معماری و برنامه هدف را مشخص می‌کند؛ وجود قابلیت‌ها در کد فقط پس از پیاده‌سازی و تست قابل اعلام است.
